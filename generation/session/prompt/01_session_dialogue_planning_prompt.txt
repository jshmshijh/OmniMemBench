You are designing dialogue flow for sessions in a multimodal conversational memory benchmark.

【Task】
Given a session outline, evidence pieces that must appear in this session, and summaries of previous sessions, design:
1. The dialogue flow (phases) for this session
2. Where each evidence piece naturally fits
3. A detailed summary of what happens in this session

【Meta-Level Understanding】

The dialogue you design will become a TEST INPUT for a multimodal memory benchmark:

1. A tested model receives ALL session dialogues (every word from both user and assistant) as memory context.
2. It also receives the actual multimodal files (images, audio, video) embedded in those dialogues.
3. It is then asked a question requiring cross-session reasoning and/or media perception.

**The dialogue text is the exam paper, not a real conversation.** Two categories of information must be protected:

- **Category A — Multimodal perceptual content:** What a media file depicts/sounds like/shows. Must ONLY be obtainable by perceiving the actual media. Dialogue text must not describe, summarize, characterize, or react to specific media content.
- **Category B — Final assembled answers:** Many questions require collecting evidence fragments from multiple sessions and/or combining text with media perception. This final conclusion must NOT appear anywhere in the dialogue. Individual evidence fragments scattered across sessions are fine — but no character should state the assembled result.

**Critical distinction:** Text evidence carrying answer-relevant information IS allowed — it is deliberately planted across sessions. What is NOT allowed is anyone performing the assembly and stating the conclusion.

【Informed Perception Model】

For each multimodal evidence piece you have three layers:

1. **caption**: Actual content description. Use internally for coherent, non-contradictory planning.
2. **context_hint**: Sanitized topic signal (e.g., "related to a musical performance"). This is the MAXIMUM detail level your output may expose about the media.
3. **question**: The benchmark question this evidence serves. Tells you exactly what information must NOT be inferable from dialogue text alone.

**The precision test:** For each multimodal evidence piece: "If someone reads my entire plan output but never sees/hears the actual media, could they answer the associated question?" If yes → leakage. If no → correct.

**Using context_hint as output ceiling:**
- READ the caption to understand the media fully.
- WRITE your output at context_hint granularity or below.
- CHECK against the question to ensure nothing answer-critical leaks.

Example: Caption says "a red acoustic guitar leaning against a wooden chair", question asks "What color is the instrument?", context_hint says "related to a musical hobby":
- ✓ "a hobby-related item" (at context_hint level)
- ✗ "guitar", "red", "instrument", "wooden chair"

【Field Responsibilities】

| Field | Role | Describes | Must NOT contain |
|---|---|---|---|
| `phase description` | The Stage | User behavior, conversational context, setting, mood | Media attributes, what files depict/sound like |
| `integration_hint` | The Entrance | Why now (motivation), where in flow, what user expects AI to do | For mm evidence: any words about what media contains |
| `summary` | The Narrative Thread | Session-level story arc, topic flow, mood shifts | Media judgments; must give each evidence a separate sentence; mm sharing uses neutral language ("shares a file") |

---

【Anti-Leakage Rules】

**Core Rules:**
- **Rule 1 — No media description (Category A):** Check each phrase against the question. If it helps answer → remove.
- **Rule 2 — No final-answer assembly (Category B):** No character assembles scattered evidence into a conclusion.

**High-Danger Patterns (special cases of Rules 1 & 2):**

| Pattern | What it means | Bad example | Good alternative |
|---|---|---|---|
| **Media judgment interaction** (Rule 3) | User asks assistant to evaluate/classify/verify media against criteria | "Check whether the image meets formatting criteria" | "Upload file, ask assistant to archive it" |
| **Benchmark question echoing** (Rule 4) | User asks a question identical/equivalent to the benchmark question | "What code should this be tagged with?" (= benchmark Q) | "Adding this to the transit case studies folder" |
| **Combinatorial leakage** (Rule 5) | Text + mm evidence in same phase combine to reveal the answer | Bridging language connecting text and mm evidence | Separate sentences, no bridging language |
| **Cross-phase leakage** (Rule 6) | Info across phases narrows down the answer | Trace what reader accumulates; check if answer becomes inferable | Use question as guide |
| **Summary propagation** (Rule 7) | Summary passed to future sessions contains judgments | "The image showed a coastal scene" | "shared a file", "uploaded something for the archive" |

---

【Guidelines】

1. **Dialogue Flow**
   - Design phases (NOT individual turns). Each phase = a chunk of conversation expanding into 1-3 turns later.
   - Phases don't need logical progression — real conversations jump topics, go on tangents.
   - Should feel like a real human chatting with an AI assistant.

2. **Evidence Integration**
   - Each evidence piece in exactly one phase.
   - Use caption knowledge for better placement (thematically compatible phases) — but output text stays at context_hint level or below.
   - Use the EXACT evidence_id from the input list.

3. **Phases Without Evidence**
   - Not every phase needs evidence. Include non-evidence phases for natural flow.

4. **Multi-evidence Phases**
   - When a phase has both text and mm evidence, watch for combinatorial leakage.
   - Write each integration_hint standalone — no causal/temporal connectors between evidence pieces.
   - In summary, describe text and mm evidence in separate sentences.

5. **Temporal Consistency**
   - When referencing previous sessions, be consistent with actual dates.
   - Prefer explicit references ("when we set that up", "in our earlier conversation") over time-based references ("yesterday", "last week") unless the date gap genuinely matches.

- Phase count is flexible
